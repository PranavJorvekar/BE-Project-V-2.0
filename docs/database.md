# Database Architecture

The data layer is managed using **Prisma ORM** with a relational structure designed for multi-project orchestration and detailed engineering task tracking.

## Entity Relationship Summary

The system revolves around the `Project` model, which acts as the root for all planning data.

### 1. Project Management

- **`Project`**: Stores meta-information (name, description, tech stack, timeline) and the current generation status.
- **`Employee`**: A global directory of available talent across the organization.
- **`TeamMember`**: A project-specific assignment of an `Employee`. This captures project-specific metrics like available hours and assigned tasks.

### 2. Planning Hierarchy

- **`Epic`**: Belong to a `Project`. Represents high-level phases. Stores total effort hours and task counts.
- **`Task`**: Belong to an `Epic`. This is where the core engineering work is defined.
  - **Fields**: Fit score, AI reasoning, skills required, effort (hours), and "Definition of Done" (JSON).
  - **Assignment**: Linked to a `TeamMember` (nullable before generation).

### 3. Risk Management

- **`Warning`**: Belong to a `Project`. Generated by the Risk Detector agent.
  - **Fields**: Severity, affected area, problem description, and recommendations.

## Prisma Schema Details (`schema.prisma`)

- **Type Safety**: Enums are used for `Status`, `Priority`, and `Severity` to ensure database-level data integrity.
- **Cascade Deletes**: All relations from `Project` (Epics, Tasks, TeamMembers, Warnings) include `onDelete: Cascade`. Deleting a project removes all its associated planning data instantly.
- **SQLite Support**: While designed for PostgreSQL, the current schema is compatible with SQLite for easy local setup.

## Key Relationships

- `Project` (1) ↔ (N) `Epic`
- `Epic` (1) ↔ (N) `Task`
- `Project` (1) ↔ (N) `TeamMember`
- `Employee` (1) ↔ (N) `TeamMember`
- `TeamMember` (1) ↔ (N) `Task`
